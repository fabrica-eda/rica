# RV64：次のIPC × クロック改善計画

検討日: 2026-09-05。実装基準: `672dea0`、実機IPC記録: `1a50ecb`。
対象は LFE5UM5G-85F / CABGA381 / speed 8。

**第一試作は完了した（2026-09-06）。64行BTB＋2-bit方向予測＋8段RASを採用する。**
CPU 124.8 MHz／メモリ62.4 MHzを維持し、setup +11 ps／hold +290 ps、
実機100/100 ELFsが合格した。既存4診断の処理率は、各3回の中央値で
幾何平均 **1.2228倍（約22.3%向上）**。実装と最終測定は
[小型予測器の評価](RV64_COMPACT_PREDICTOR.md)に記録した。

後続の[JTAG修正](RV64_JTAG_FIX.md)で受信エッジの競合を解消し、8-byte転送へ復帰した。
現行版も固定PLLで100 ELFs／134実行が合格し、CPU性能は先の認定版から0～1 cycleの差。

以下は2026-09-05に静的4 KiB版の実機IPCから策定した計画と、その根拠の記録。
単発行インオーダーと4 KiB L1Iを基盤にする方針は維持する。次はタイミング余裕の拡大、
データアクセスの待ち短縮、残る方向誤り、命令補充・容量を実機の処理時間で比較する。

用途の指定がないため、既存の整数・分岐・呼出し・load/storeの4診断を等しく重視する。
大きなプログラムが主用途なら命令キャッシュ、配列処理ならLSUの優先順位を上げる。
これらの診断だけで汎用アプリケーションの最速を証明したとは扱わない。

## 評価する性能

`IPC = minstret / mcycle`、`命令処理率 = IPC × CPUクロック`。
MHzを掛けた値の単位は百万退役命令/秒で、DMIPSではない。
同じELF・同じ測定区間なら速度比は `旧mcycle / 新mcycle` で比較できる。
コンパイラやISA拡張で命令数が変わる場合は、同じ仕事が完了する実行時間を比較する。

CPU **124.8 MHz**、メモリ **62.4 MHz**のPLL設定と2:1・位相0の関係を維持する。
実機IPCは起動・キャッシュ初期化から終端storeの応答までを含む。
JTAGロードは含まず、周波数は外部計測器による独立測定値ではない。
[基準記録](../toolchain/measurements/2026-09-05-rv64-ipc-clock/README.md)を比較元とする。

出典は[実機summary.json](../toolchain/measurements/2026-09-05-rv64-124p8-hardware/summary.json)。
4種類のpipelineイベントはmemory→redirect→dependency→frontendの優先選択で数える。
命令の退役とイベントが重なる場合があり、予測器イベントも独立に重なる。
**これはCPIの損失内訳ではないため、割合を足したり、そのまま削減可能な時間と解釈したりしない。**
定義は[Core](src/Core.veryl)と[カウンタ仕様](README.md)にある。

現在の[静的予測器](src/StaticBranchPredictor.veryl)は常に順次実行を予測する。
そのため`alu_chain`のtakenループ分岐255回は全て修復を要する。
`call_return`では条件分岐の方向誤り255回に対して修復は767回あり、
間接呼出し・復帰も改善対象になる。静的構成の`btb_miss`は全制御移行を数えるため、
BTBの容量不足を示す測定値としては使わない。

## 追加実験：初回取得と定常ループを分ける

RTLを変更せず、元の2診断のループ回数と期待結果だけを変えた。
リンクスクリプト、命令長、命令配置を揃え、6 ELFs × 2通りの同時エッジ順序で
**12/12モデル実行が合格**。元の反復数では、保存済み4 KiBモデルの命令数・全区間cycles・
最初のcommit・実行区間が完全一致した。

| 診断 | 反復数 | commit数 | 最初〜最後のcommit区間 cycles |
| --- | ---: | ---: | ---: |
| `alu_chain` | 256 | 4,615 | 6,712 |
| `alu_chain` | 512 | 9,223 | 13,368 |
| `alu_chain` | 768 | 13,831 | 20,024 |
| `capacity_3k` | 8 | 6,173 | 8,580 |
| `capacity_3k` | 24 | 18,493 | 21,028 |
| `capacity_3k` | 40 | 30,813 | 33,476 |

反復数を増やした差分を取ると、短いALUループは**18命令 / 26 cycles = 0.692308 IPC**、
3 KiBループは**770命令 / 778 cycles = 0.989717 IPC**。
各診断の2つの差分で同じ値が得られた。起動・初回補充など一定の費用を差分で除いた
追加反復の値であり、実機全区間の0.660466 / 0.696447 IPCとは測定範囲が異なる。

長いループでは単発行の命令供給・依存ALU処理がほぼ1命令/cycleまで動く。
両ループに共通する毎反復8 cyclesの上乗せは、taken分岐とその後の取得再開が
主因と推定する。厳密な原因別の帰属は、次段階でcycle traceを取って確認する。
この結果から、小型の分岐予測を次の第一候補にする。

[実験ログ・集計・再現スクリプト](../toolchain/measurements/2026-09-05-rv64-next-performance/README.md)を保存した。

## 第一試作：小型の分岐予測

初期案は**64エントリ・1 wayのBTB、各エントリの2-bit方向カウンタ、8段RAS**。
BTBは分岐元PC、分岐先、命令種別を保持し、RASは関数からの復帰先を保持する。
32エントリ版も比較し、必要な精度を保てる小さい方を選ぶ。
論理上のBTBは約4 Kbit、RASのアドレス部は256 bit。タグ・復旧状態や実際の
LUT/EBR消費は別に必要で、合成・配置配線後に確定する。

| 設計箇所 | 方針 |
| --- | --- |
| lookup | 1要求/cycleの受付を維持し、同期読出しと短い登録段でPC経路を分割する |
| 予測種別 | 条件分岐は2-bit、JAL/JALRはBTB、復帰はRASを優先する |
| 更新 | 退役した命令で学習し、同一行の読書き衝突を明示的に処理する |
| RV64/Zca | 現在の32-bit物理PC範囲を維持し、圧縮callのPC+2を正しくRASへ積む |
| 復旧 | 投機RASと退役済みの状態を区別し、誤予測・例外・FENCE.Iで古い応答を破棄する |
| Core接続 | 静的構成で省略した予測PCの保持・照合を新モードに合わせて再設計する |

既存bimodalは256-entry・2 way BTB、16段RAS、大きい予測管理を共有している。
その選択フラグだけを切り替える案の性能と、小型の新構成の性能は分けて比較する。
`branch_pattern`のN,N,T,Tは2-bitカウンタだけでは十分に予測できない。
まずループ・分岐先・復帰の改善を測り、残る方向誤りに対して短い履歴のgshareを
追加候補にする。今回の2診断だけに合わせた特殊なループ処理は入れない。

設計目標への感度として、18命令ループの上乗せを8→4 cyclesにできれば
定常IPCは0.818182、速度比は**1.182倍**。8→2ならIPC 0.900000、**1.300倍**。
これは上乗せ削減を仮定した計算であり、予測器実装の測定結果や改善保証ではない。
第一試作では8→4 cycles以下を目標にし、他の診断の退行とSTAも同時に判断する。

FPGA向けのVexRiscv公式資料にも、BTB予測とPCまでの組合せ遅延、
分岐の段分けとFmaxの取引関係が説明されている。ここでは設計上の参考にし、
別のRV32コアのFmaxや分岐ペナルティを本RV64へ転用しない。
[VexRiscv BranchPlugin](https://github.com/SpinalHDL/VexRiscv#branchplugin)。

## その後の優先順位と改良幅

| 順位 | 改良 | 根拠と進め方 | 主な制約 |
| --- | --- | --- | --- |
| 2 | データアクセス待ち短縮 | `load_store`のmemoryイベントは39.89%。要求・応答の段別遅延を測り、小型store buffer＋同一アドレス転送を先に比較する。必要なら1〜2 KiBのCPU側データキャッシュを試す | 例外・順序・部分書込み・非整列アクセス・tohost応答を維持する。現診断は1 wordの反復であり、配列の帯域や容量の証拠にはならない |
| 3 | 命令補充の連続化 | 現在は64-bit行・未完了要求1件。16/32-byteの連続補充、必要な行を先に渡す方式、2件の要求管理を小さい案から比較する | 既に次行先読みはある。要求の多重化ではsequenceも拡張し、redirect/FENCE.I後の古い応答を区別する |
| 3 | 8 KiB L1Iの成立 | 既存モデルの6 KiB検査は20,184→10,856 cycles、同区間で1.859倍。大きなコード向けの有力候補 | 8 KiB版は124.8 MHzで未認定。小さい4診断の実行区間は変わらず、初期化は256 cycles増える |
| 4 | FENCE.Iの無効化短縮 | 現在の4 KiBは256行を走査。世代タグで通常の無効化を短くする案を比較する | 世代番号が一周する前の全走査、reset時の有効状態確立、進行中の補充と取得queueの無効化が必要。FENCE.I全体が1 cycleになるとは限らない |
| 継続 | 配線・タイミング余裕の拡大 | 取得・decode・forwardingを局所化し、同じ124.8 MHzで変更余地を増やす | 新しい制御線やwide muxを追加するたびに配線後のsetup/holdを確認する |
| 後段 | 周波数増加・2命令発行 | 命令・データ供給の改善後に、独立命令を含む実用ワークロードで評価する | 今のALU診断は依存列。2命令発行を加えても同じ列を2命令/cycleでは実行できず、RFポートとbypassの増加も大きい |

store bufferには退役が確定したstoreだけを入れる。FENCE/FENCE.Iやtohostで必要な
書込みの排出を完了し、MMIOは順序と副作用を保つ経路へ通す。
部分書込みからloadへ転送する場合は、要求された各byteが揃っていることを検査する。

8 KiBモデルの6 KiB検査は起動込みでも20,458→11,386 cycles、1.797倍。
一方、小さいALUは起動込みで約3.7%遅く、`fence_i`は約72.6%遅い。
容量拡大、補充、無効化の改善を個別に測り、用途に応じて構成を選ぶ。
出典は[同一RTLの0/2/4/8 KiB比較](../toolchain/measurements/2026-09-05-rv64-124p8/summary.json)。

メモリ実装はECP5の同期RAMのポート・出力段・読書き衝突条件に合わせる。
段削除やポート追加は[Memory User Guide §4](https://www.latticesemi.com/view_document?document_id=50466)と
現在の[HardwareMemory](src/HardwareMemory.veryl)で成立を確認する。
store bufferやデータキャッシュを加えた場合は、FENCE.I後の取得に先行storeが見えることも検査する。
[RISC-V Zifencei仕様](https://docs.riscv.org/reference/isa/v20240411/unpriv/zifencei.html)。

## クロックを先に上げない理由

計画策定時の静的版のsetup余裕は64 psで、最小の端点は命令キャッシュの`proposed_request_q`。
続いて`rx_alu_op_q[0]`が108 ps、`cm_arithmetic_q[60]`が113 ps。
最悪の1経路だけを直せば大きく周波数を上げられる状態ではない。
根拠は[最終STA](../toolchain/measurements/2026-09-05-rv64-124p8/texo-final-sta.json.gz)。

124.8→126 MHzの処理率増加はIPC一定なら約0.96%だが、周期は約76.3 ps短くなる。
現状の64 ps余裕を上回るため、単にPLLを126 MHzへ変更する案は採用しない。
150 MHzなら約20.2%の増加だが周期短縮は約1.346 nsで、複数経路と関連クロックの再設計が必要。
これらは周期の算術比較であり、変更後のSTAや達成Fmaxの測定値ではない。

## 実装・検証の進め方

1. 現在のモデルに観測用のcycle traceを設け、退役有無、分岐修復、warm hit、
   demand miss、補充待ち、scrub、LSU要求/応答を分ける。まずモデル側で行い、
   実機への観測回路追加はタイミングへの影響を別途確認する。
2. 静的4 KiB版を比較基準に、小型BTB→方向予測→RASを段階的に比較する。
   同期lookupの遅延、方向誤り、target miss、復帰誤りを別々に記録する。
3. RV64I/Zca・CSR・FENCE.Iを維持し、誤経路のstore、例外と分岐の競合、
   RASのoverflow/underflow、read/write衝突、自己書換え、両エッジ順序を検証する。
4. 各候補を固定PLLで配置配線する。setup/holdが非負で、CPU・メモリ・関連境界の
   検査範囲が欠けないことを必須とする。未達候補のIPCを採用性能とは呼ばない。
5. 合格bitstreamを実機へ書き込み、98 ELFsと11カウンタを再検査する。
   基準版・候補版を同一条件で反復実行し、初期化込みIPC、時間、診断4本の
   速度比の幾何平均、容量/FENCE.Iの退行、LUT/FF/EBR、STA、ハッシュを記録する。
6. 実用処理のコードを固定して評価対象へ追加する。乗除算などのISA拡張を検討する場合は、
   同じ仕事量の時間で判断し、命令数の減少による効果も記録する。

8-byte JTAG転送の修正と再検証は完了した。現行の性能測定は[JTAG修正版](RV64_JTAG_FIX.md)を使い、
次の配置でもJTAG追加ゲートと同じSHAの実機検証を通す。公式hard-macro timingとreset／CDC解析は残る。
