# RV64 JTAG zero-response reproducer and repair checks

The [Japanese investigation report](../../../riscv/RV64_JTAG_FIX.md) records
the cause, controlled experiments, fix and limits. The board is LFE5UM5G-85F,
CABGA381, speed 8, with unchanged 124.8/62.4 MHz CPU/memory PLL clocks.
Use one XVC client at a time; these physical probes reset the board's test
state and may overwrite the test program in RAM.

The fixed image is
`riscv/build/riscv-hardware-compact-4k-124p8-20260906-jtag-falling.bit`, SHA-256
`5ac5d9e05e0cd2b82aec0b51039fae028f0081c5aa0c738e1bc89bfa69e15b12`.
It passed all 100 physical ELFs using eight-byte writes, with 134 total ELF
executions, plus the former 48 WRITE64 corruption probes.

## Diagnostic tools

- `probe.py` records IDCODE, direct PLL lock through ER2, all 32 ER1 status
  selector bits, and five transaction sequences. `--program` loads the
  hash-checked image first. It is a recorder: exit zero alone is not a PASS;
  inspect magic `0x52`, version `5`, sequence and uniform per-selector samples.
- `route-probe` reads the original Texo architecture and checkpoint, finds
  unoccupied JTDI detours, and records their exact PIPs and modeled delays.
  It excludes wires already used by other nets. `route_eco.py` packs one
  detour and checks that only the listed routing arcs changed.
- `clock_eco.py` changes the frozen bad configuration's clock polarity for
  `--scope all` (132 FFs), `shift` (128), or `control` (4). It checks that
  no unrelated FF shares a changed clock mux and that routing is unchanged.
- `jtag-sta` reconstructs connectivity from checkpoint net-delay records and
  checks JTCK register paths at 6 MHz using pinned Texo `7b372da` and the same
  `8_5G` cell tables. The gate also requires all 261 JTCK FFs to be falling-edge,
  no separate UPDATE clock, 515 setup/hold checks, and exactly three named
  external input endpoints. It does not fabricate JTAGG timing arcs.

The ECO images are diagnostic artifacts, not fully timed release candidates.
The final repair is in `JtagDebugTransport.veryl`, generated by ordinary synthesis
and place/route. It uses standard 128-bit scans; the 129-bit scans were solely
for diagnosing the edge-only ECOs.

## Checked bitgen for the current board

Run from the repository root. Supply the installed architecture path explicitly:

```sh
RICA_JTAG_ARCH=/home/user/.cache/texo/targets/LFE5UM5G-85F-texo-LFE5UM5G-85F-schema7-cache5-x86_64-unknown-linux-gnu/architecture.txdb
python3 riscv/tools/bitgen_jtag_checked.py \
  riscv/build/jtag-zero/jtag-falling.texo.json \
  --architecture "$RICA_JTAG_ARCH" \
  --audit-report /tmp/rica-jtag-audit.json \
  --bit /tmp/rica-jtag-checked.bit
```

Output paths must be new. The wrapper builds the pinned supplemental checker,
checks CPU/memory closure and the required PLL periods, runs JTCK analysis,
and rejects any main-STA unchecked endpoint outside that audited scope or the
named first CPU synchronizer. Bitgen runs only after those checks pass.
Physical qualification still applies to the exact output SHA, separately from
the structural/internal timing gate. Hard JTAGG arcs, reset recovery/removal
and bundled-data CDC characterization remain outside this model.

The recorded negative test used
`riscv/build/compact-predictor/compact64-token-next.texo.json`: its ordinary
STA says `met_timing=true`, but the checked flow exits 1 without creating a bit.
The repaired checkpoint passes and regenerates the physically tested SHA.

## Functional and physical regression

```sh
cargo test --locked --offline -p verify-riscv --test jtag_transport_edges
cargo run --locked --offline -p verify-riscv --bin verify-riscv -- --jtag-only
cargo run --locked --offline --release -p verify-riscv --bin hardware-riscv-tests -- --xvc 127.0.0.1:3721
target/release/hardware-riscv-tests --no-program --xvc 127.0.0.1:3721 --act4
target/release/hardware-riscv-tests --no-program --xvc 127.0.0.1:3721 --act4-suite Zca
python3 toolchain/mre/rv64-jtag-write64/probe_offsets.py
```

The full commands, bit/config hashes, original failed probes, polarity A/B
results, STA outputs, regression logs and per-benchmark samples are retained in
[the evidence directory](../../measurements/2026-09-06-rv64-jtag-zero/README.md).
Preserve those records; use fresh labels/paths when repeating experiments.
